Category offsets — how each category shifts the regression

Each pre-token protocol is priced by the regression, shifted by its own category's offset. An offset is the category's median log market-cap/TVL ratio minus the global median, shrunk toward zero by n ÷ (n + 5) — categories hold few live tokens, so an unshrunk median is mostly noise. Categories with no live tokens get no offset.

How the implied value is built

Each pre-token protocol's implied value comes only from the sealed snapshot's own figures — no outside prices, no hand-kept list of names:

  1. Admit. A protocol is rankable when its record shows no token at all (market cap, CoinGecko id and symbol all null) and it is not a wrapped, staked or bridged product, not a versioned pool, and not an exchange. The snapshot's 40-protocol watchlist is the floor; the same rule admits the early protocols below the $50m floor too. The record is not proof: a protocol the record calls pre-token may still have a token its record does not carry, and the board says "records no token", never "has none".
  2. Fit. Regress ln(market cap) on ln(TVL), ln(age + 30 days) and the 7-day TVL change by least squares over the snapshot's clean live tokens — market cap and TVL above zero, no barred category, no versioned name, market-cap/TVL at most 3 (a version misattribution or a 400× outlier must not set any multiple). The fit runs at run time from the snapshot — no coefficient is hardcoded. On this snapshot ln(mcap) = + · ln(TVL) + · ln(age + 30) + · growth, fit on clean tokens, residual sd , R² = . The TVL slope is below 1, so the implied multiple falls as TVL rises: a flat multiple would overvalue the largest protocols several times over. Growth and age enter at their fitted coefficients — small, because that is what the snapshot's own figures say.
  3. Shrink the category offset. For each category, take the median of its live tokens' ln(market cap/TVL), subtract the global median, and shrink it toward zero by n ÷ (n + 5), where n is the category's live-token count. A category with one live token cannot set its own multiple — Risk Curators has exactly one comparable, and its raw ratio would triple every row in it — and a category with none gets no offset. The table below shows every category's raw median log ratio and the shrunken offset the board uses.
  4. Guard, don't clamp. Implied value = exp(fit + offset). The multiple then passes a wide sanity guard [0.002, 3.0] that binds on no row of this board: the guard is a guard, not the model. No row's value is set by a bound. The detail view shows each number for every protocol, including whether a guard bound.
  5. Token odds are shown, never priced in. The board carries a token-odds column: the share of protocols in this snapshot whose record carries a token, by age bucket times the protocol's category rate, capped to [0.05, 0.95]. It is a record rate in this cross-section — older protocols and token-heavy categories score higher — not a prediction that a token launches, so it stays out of the implied value. Age runs from the listing date to the snapshot date, 2026-11-14, or the median age of the admitted protocols () when no listing date is recorded; age feeds the value through its fitted coefficient and the farm plan's hold time.
  6. Rank. Sort by implied value, highest first. The board is the claim; the snapshot's record is not proof a token will ever launch.
